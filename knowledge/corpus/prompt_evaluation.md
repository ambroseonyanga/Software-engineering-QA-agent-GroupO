## 10-Case Prompt Evaluation

Project: Software Engineering QA Agent
Prompt Version: 1.0
Model: Qwen3 8B
Deployment: Local using Ollama

Evaluation focus: Requirements , candidate QA test proposals

Purpose: Establish a Week 2 baseline for the model-backed QA capability. Each case tests whether Prompt v1.0 can interpret a requirement, identify testable behavior, generate appropriate candidate tests, handle ambiguity or missing information, and avoid inventing facts.

### Overall Findings

All 10 cases passed at the baseline level. Qwen3 8B showed that it can analyze requirements, identify testable behavior, generate candidate QA tests, and recognize ambiguous or incomplete requirements.

The main weakness was assumption leakage. In several cases, the model introduced reasonable QA expectations or common implementation practices and sometimes treated them as requirement-supported behavior. This was most noticeable in TC02 and TC08.

The model performed better when the prompt explicitly required a distinction between requirement-supported tests and assumption-based tests. This was particularly clear in TC05, TC06, TC07, and TC10.

### Implications for Prompt v1.1

Classify each proposed test as requirement-supported, assumption-dependent, or recommendation.

Keep unsupported best practices in a separate recommendations section.

Do not include an expected result unless it is stated or directly implied by the requirement.

When a requirement is vague, ask for clarification instead of filling the gap with assumed criteria.

Make the connection between each test and the requirement explicit so coverage can be traced.

| TC03 | Boundary | The system shall allow a user to purchase between 1 and 10 items in a single order. | Test the lower and upper boundaries and invalid values while keeping the tests tied to the stated range. | Qwen3 correctly identified the range rule and generated tests around 1, 10, zero, and values above 10. | TC04 | Negative / Security | The login feature accepts a registered email address and password. | Identify the core login behavior and propose normal, negative, edge, and relevant security tests without inventing login outcomes or security controls. | Qwen3 correctly identified the core login behavior and generated normal, negative, edge, and security-focused tests. It recognized that several security and validation details were unspecified. However, it introduced assumptions about dashboard redirection, case-insensitive email matching, specific error messages, sanitization, XSS handling, and logging. | PASS with observations | Broad and useful QA coverage, but some expected behaviors were not supported by the requirement. |
| TC05 | Ambiguous | The system should be fast and easy to use. | Determine whether the requirement is sufficiently testable. Identify the missing measurable criteria needed to create reliable tests. | Qwen3 correctly determined that the requirement was ambiguous and not sufficiently testable. It identified the need for measurable performance criteria, usability criteria, expected outcomes, and additional information before reliable tests could be designed. | PASS | The model handled ambiguity appropriately and did not treat example criteria as established requirements. |
| TC06 | Incomplete | The system shall send a notification when a transaction is completed. | Identify the directly supported notification behavior and explain what information is missing. Do not assume the notification channel, recipient, timing, or content. | Qwen3 correctly determined that the requirement was incomplete. It identified the missing notification channel, recipient, timing, content, and failure handling. It separated the directly supported behavior from tests that would require assumptions. | PASS | Good distinction between supported behavior and missing information. The model followed the no-guessing constraint well. |
| TC07 | Conditional / Conflicting | The system shall allow users to cancel an order at any time. Orders that have already been shipped cannot be cancelled. | Identify the two conditional behaviors and test the boundary between shipped and non-shipped orders without inventing order states or cancellation rules. | Qwen3 correctly identified that cancellation is allowed for non-shipped orders and denied for shipped orders. It identified ambiguities around the meaning of shipped, order states, timing, and failure behavior. It also labelled scenarios involving transitional states, partial shipments, and time-based cancellation as assumptions. Some expected outcomes, such as displaying an error message and marking the order as cancelled, were not explicitly supported. | PASS with observations | Strong conditional reasoning and better separation of assumptions, although some expected outcomes were still unsupported. |
| TC08 | Security | All user passwords must be securely stored. | Identify what can be tested from the requirement and avoid inventing specific encryption algorithms, hashing methods, password policies, or implementation details. | Qwen3 correctly recognized that securely stored is ambiguous and that the requirement does not specify a particular hashing or encryption mechanism. It generated relevant security-focused tests and identified missing information. However, it classified some additional behaviors, such as preventing password exposure in logs or APIs and requiring password hashing, as requirement-supported. It also introduced assumptions about salts, key derivation, work factors, and key management. | PASS with significant observations | Strong security reasoning, but the model needs to distinguish more carefully between the stated requirement and security best practices. |
| TC09 | Performance | The system shall support 500 concurrent users with acceptable performance. | Identify the concrete 500-user requirement and explain why acceptable performance is ambiguous. Do not invent response-time, throughput, hardware, or workload thresholds. | Qwen3 correctly identified that 500 concurrent users are the concrete capacity requirement while acceptable performance is ambiguous. It avoided treating response-time, throughput, spike-load, and resource thresholds as established requirements and labelled specific values as assumptions. However, it interpreted acceptable performance as remaining responsive, avoiding degradation, and monitoring resources without those criteria being explicitly defined. | PASS with observations | Good handling of an ambiguous performance requirement, with a remaining need to distinguish the literal requirement from reasonable QA interpretations. |
| TC10 | Insufficient Evidence | Determine whether the payment feature is secure. | Determine whether the requirement is testable. If it is not, identify the missing security criteria without inventing controls, workflows, compliance standards, or implementation details. | Qwen3 correctly determined that the requirement was not sufficiently testable because secure was not defined. It identified missing security criteria, controls, workflows, environment details, and measurable outcomes. It avoided presenting specific security controls or compliance standards as established requirements. A minor issue was the inclusion of performance metrics, which were not necessarily relevant. | PASS | Strong handling of an underspecified security requirement. The model appropriately identified the need for clearer acceptance criteria instead of manufacturing test criteria |
